日期：2026-08-05

## 1. 结论（2026-08-06 更新：0.62.0）

**Core 模式已转为默认并可发布。**`UNTERM_CORE_CLIENT=0` 保留旧的单进程形态。

转默认的三个前置条件已全部达成：MCP 迁入 Core（M1-03c 阶段二，四步）、
Core 崩溃可重连、TUI 与端到端渲染实测。

一次误判值得记下来：转默认前我曾以为「Core 模式下 agent 的 session.focus
不生效」而回退。实际是我把侧栏行首的**tab 序号**读成了 pane id——焦点一直
是对的，终端内容与引擎的 is_active 始终一致。真实差异只有一条且是外观级：
重开窗口时被领养的活跃会话会排到第一个 tab，即 tab 顺序不跨重启保真
（会话本身、scrollback 与分屏都保真）。教训：报告缺陷前先确认自己读的是
哪一个标识符。

两轮审计共发现并修复 **13 个发布级缺陷**：

- 第一轮逐功能核对「这个功能在 Core 模式下还对吗」，得 8 个（第 3 节）。
- 第二轮把 release 制品当成用户拿到的东西真机跑一遍，得 5 个（第 3b 节）。
  这一轮是必要的：**在此之前 release 制品从未被真人跑过**，所有验证都在
  debug 上做。第一个命令就撞出了确认门禁的问题。

其中 12 个是单元测试发现不了的——只在重启一次、另一个进程死掉之后、
或界面切到中文之后才显形。

## 3. 本轮发现并修复的缺陷

按严重度排序。**每一条都是真机或跨重启才暴露的**：

1. **Core 崩溃后窗口看着正常**——GUI 存活、响应正常，屏幕是上一帧缓存，
   输入无反应且无任何说明。M1 门禁禁止把崩溃报成正常，静默冻结是最糟的
   一种。现检测事件流非预期中断并画出贯穿窗口的红色告知条。
2. **Core 模式下会话每次重启翻倍**——领养既有会话后又按保存的 cwd 列表
   各开一个。实测 6 pane 重开变 9。现仅冷启动时恢复额外 tab。
3. **Fleet 走错引擎**——多 agent 并行对进程内引擎建会话，Core 模式下
   落在空世界里，GUI 永远看不见。
4. **statsbar / cockpit / 录制导出 / scrollback-PNG 走错引擎**——同因，
   四处后台线程直接构造本地引擎。现统一走 `host_engine()`。
5. **光标错位**——确认横幅接进 status_bar_height 后，终端高度随「是否有
   待确认」突变，而 PTY 行数只在窗口 Resized 时同步：程序以为 N 行、
   画布按 N−1 行画。现横幅改为覆盖层，不占布局高度。
6. **Core 模式空转 IPC**——每个空闲 tick 对每个 pane 一次 `screen_revision`，
   即每 pane 一次 TCP 往返，20 pane 窗口每 tick 20 次，只为问「变了吗」。
   现改读 FrameCache 计数器（一次原子读、零上线）。
7. **窗口边缘不可拖拽**——全应用从未调用 `set_cursor`，边缘无任何提示；
   抓取带固定 6 物理像素，150% DPI 下仅 4 逻辑像素。现按点计量并补全
   八向光标与 L 形转角。
8. **状态目录隔离漏洞（3 处）**——`server_info`、`settings`、
   `session_restore` 都不认 `UNTERM_STATE_DIR`：测试与 headless 运行
   读写真实用户的实例注册表、配置与会话文件。

另修一处我自己在本轮引入的：新写的错误分支把「读超时」吞进通用错误分支，
worker 第一次超时就把活着的 Core 判成已死——由 frame_cache 收敛测试当场抓住。

## 3b. 第二轮：release 制品真机验收发现的缺陷

跑 release 制品的第一条命令 `exec run` 就挂了 30 秒然后报「Unterm 没在运行」，
而当时 Unterm 正开着、其余所有 MCP 调用都在 30 ms 内成功。顺这条线索挖出
一整条坏掉的链：

1. **确认横幅问的是「exec.run: len=22…」**——预览把字节数放在最前、命令放在
   最后，一截断，被砍掉的正好是唯一能用来做信任判断的东西。安全门禁不告诉你
   在批准什么，就不是门禁，只是一个让人点「是」的提示。
   现改为命令在前、字节数在后（截断时最先掉的是字节数）。
   **为什么单测没抓到**：横幅测试喂进去的 preview 是裸命令 `"rm -rf /"`，
   而生产从来只产出 `"len=8 rm -rf /"` 这种形状。测试看不到生产的形状，
   就抓不到生产的缺陷。现已把 `input_preview` 转 pub，横幅夹具一律由它构造。
2. **客户端与服务端超时完全相等（30 s / 30 s）**——客户端必然在服务端裁决的
   同一刻放弃，真实结果永远送不到；CLI 于是编出一句「unterm GUI is not
   running，请打开 Unterm」，把人指向重启一个运行正常的应用。
   现读超时取「确认超时 + 15 s」，读超时不再复用「没运行」文案。
3. **三种阻断一律报 `user denied`**——「没有窗口可批准」「用户按了拒绝」
   「没人回答」是三件不同的事，对 agent 意味着三种不同的下一步。
   现 `GateOutcome::Block` 带原因，各说各的。
4. **中文界面下横幅溢出，先掉的是「拒绝」那个键**——`chars().count()` 量宽度，
   而「允许」是两字符四列。本地化把这行撑爆了，而最先被挤出屏幕的，
   正好是唯一能拒绝的按键。现按显示列度量，并加 zh/ja/ko 四语言宽度回归。
   横幅同时改为只覆盖终端区，不再压住侧栏的「新建会话」与设置。
5. **Windows 编辑器存的 `unterm.conf` 被静默丢弃**——PowerShell 的
   `Set-Content -Encoding utf8` 和 Notepad 都写 UTF-8 BOM，BOM 粘在第一个键上，
   整份配置无效且不报错。在 Windows 优先的产品里，用户最可能采用的编辑路径
   正好是失效的那条。现读取时剥 BOM。
   （这条是我自己的测试脚本踩中的——脚本写完配置发现没生效，追下去才知道
   不是脚本的问题。）

顺带确认横幅本身确实会绘制、按键可答、审计日志与客户端报错时间戳对得上。

## 5. Core 模式转默认前的缺口（0.61.1 时的记录，已全部消除）

已验证可用：会话建于 Core、杀 GUI 会话存活、重开领养且 scrollback 与
分屏排布保真、MCP 建会话落 Core、崩溃有告知、事件驱动渲染。

仍缺：

- **MCP server 生命周期仍随 GUI**。Core 自带一个 headless MCP 作故障转移，
  但 GUI 在场时 agent 连的是 GUI 那个——GUI 退出，agent 的控制面就断了。
  单一 MCP + McpHost 反向 IPC 是终态（M1-03c 阶段二）。
- **Core 崩溃后只能重启，不能重连**。告知条是诚实的，但恢复路径还是
  「重启 Unterm」。
- **GUI 渲染帧率与 TUI 抖动未量化**。需目视与录屏，不在自动化范围。
- **Core 模式端到端按键延迟未测**。现有数字是组件级。

## 5c. 0.62.0 实测（Core 为默认）

| 指标 | 实测 | 口径 |
|---|---|---|
| 端到端 按键→屏幕 | **p50 16.0 ms**，p95 31.7 ms，min 12.2 ms | 单条持久 MCP 连接，写入后轮询直到出现在渲染屏幕 |
| 对照：纯 IPC 读 | p50 0.25 ms，p95 0.44 ms | 同一连接的 screen.text |
| GUI 空闲 | CPU 0.004%，内存 130.7 MB | 20 秒 |
| Core 空闲 | CPU 0.148%，内存 12.6 MB | 20 秒 |

**16 ms 落在一个 60 Hz 帧内**，其中 IPC 只占约 0.5 ms（两次往返）；其余是
ConPTY 与 shell 自身的回显成本，与构建方式无关。

**测量口径的坑**：第一次量到 11.7 秒，是因为每次轮询都启动一个新的
`unterm-cli.exe`——量到的是进程启动开销而不是终端延迟。换成单条持久连接
后才是真实数字。

功能验收（Core 默认，release 制品）：15 项全扫零失败；杀掉 GUI 后
`session list` 与 `exec.run` 仍可用；重开 GUI 领养会话且 scrollback 完好；
跨进程确认横幅在窗口正确绘出完整命令与三个按键。
